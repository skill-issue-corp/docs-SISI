# Рекомендации по PR
Этот документ излагает рекомендации по отправке изменений в атмосферу.
Похоже на конвенции кодирования проекта, но отличается от них: у атмосферного кода есть особые соображения, которых следует придерживаться при создании новых функций или написании исправлений ошибок.

```admonish question "Но почему?"
Атмосфера находилась в плачевном состоянии. Она прошла через несколько рефакторингов — как от её изначального создателя в SS14, так и от других мейнтейнеров, последовавших его примеру.

Были внесены крупные изменения, которые молча сломали ключевые атмосферные функции, что негативно повлияло на игру в целом до такой степени, что для противодействия воспринимаемым последствиям были приняты плохие проектные решения.

Недавно мейнтейнеры (в основном просто я, Roomba) предприняли усилия по полному повторному документированию атмосферы и написанию тестов для неё.
Таким образом, эти рекомендации отражают все уроки, которые я извлёк на данный момент при исправлении, поддержке и расширении атмосферы.
```

## Общие конвенции кодирования
### Повторные тезисы
Вам следует быть знакомым с конвенциями кодирования проекта и их основными принципами:
- **Не копируйте и не вставляйте код.**
- **Не используйте магические строки/числа.**
- **Полностью комментируйте назначение вашего кода, а не просто то, что он делает.**

### Все члены должны быть задокументированы независимо от уровня доступа
Весь код должен быть задокументирован, даже члены `private`, даже если это простые вспомогательные методы или поля данных.

Это значительно помогает мейнтейнерам в проверке вашего кода и помогает контрибьюторам составить общую картину того, как функционирует атмосфера.

Как правило, публичные методы должны иметь надлежащее описание, документацию параметров, оговорки, которые следует учитывать, документацию возвращаемого значения метода, если применимо, а также пример, если применимо. Распространение этого уровня документации на члены `private` приветствуется.

```csharp
/// <summary>
/// Вычисляет безразмерную долю газа, необходимую для выравнивания давления между двумя газовыми смесями.
/// </summary>
/// <param name="gasMixture1">Первая газовая смесь, участвующая в выравнивании давления.
/// Эта смесь должна быть той, от которой вы всегда ожидаете наибольшего давления.</param>
/// <param name="gasMixture2">Вторая газовая смесь, участвующая в выравнивании давления.</param>
/// <returns>Число с плавающей запятой (от 0 до 1), представляющее безразмерную долю газа, которую нужно передать от
/// смеси с более высоким давлением к смеси с более низким давлением.</returns>
/// <remarks>
/// <para>
/// Это должным образом учитывает эффект
/// слияния газа от входа к выходу, влияющий на температуру
/// (и, возможно, повышающий давление) на выходе.
/// </para>
/// <para>
/// Предполагается, что газ расширяется свободно,
/// поэтому температура газа с большим давлением не меняется.
/// </para>
/// </remarks>
/// <example>
/// Если вы хотите рассчитать моли, необходимые для выравнивания давления между входом и выходом,
/// умножьте возвращённую долю на моли источника.
/// </example>
public float FractionToEqualizePressure(GasMixture gasMixture1, GasMixture gasMixture2) {...}
```

### Подсистемы должны находиться в собственном partial-классе
Под подсистемами понимаются процедуры, которые атмосфера выполняет во время обновления.
Это крупные состояния обработки, такие как `Revalidate`, `TileEqualize`, `ExcitedGroups`, `DeltaPressure` и т. д.

Большая часть логики, относящейся к этим подсистемам, должна находиться в собственном partial-классе в `AtmosphereSystem` в формате `AtmosphereSystem.<Subsystem>.cs`.

Любые импорты `[Dependency]` должны находиться в корневом partial-классе `AtmosphereSystem`.
Любые `const` или приватные поля, которые активно используются или управляют конфигурацией для указанной подсистемы, должны находиться в partial-классе этой подсистемы.
Если эти поля `const` полезны на клиенте, они должны принадлежать статическому классу `Atmospherics`.

### По возможности избегайте god-методов
Не создавайте ужасающе длинный (например, 350+ строк кода) метод, выполняющий основную часть логики вашей подсистемы.
Разбейте ваш метод на отдельные шаги обработки, которые вызывает ваш основной метод.

Это может позволить вам превратить ваш вспомогательный метод в универсальные методы, которые можно вызывать по всей атмосфере.
Например, если вы вывели полезную математическую функцию, которая помогает выравнивать давление между двумя `GasMixture`, сделайте её публичным методом, который системы могут вызывать в `AtmosphereSystem.API`.

### Математические выводы должны быть надлежащим образом задокументированы
Для ваших математических выводов должна быть предоставлена документация для любых созданных вами функций.

Документация должна быть встроена в код в виде многострочного комментария и оформлена получитаемым образом.
Предпочтительна псевдо-LaTeX-нотация.

Хотя самодокументируемые имена переменных и однострочные комментарии на каждом шаге всегда желательны, предпочтителен общий обзор шагов, которые вы предприняли для достижения своего решения. 


### Новые дополнения должны иметь тесты
Будь то новый метод API или новая атмосферная функция, реализация должна иметь тесты, должным образом покрывающие изменения.
Тесты бесценны для атмосферы, поскольку большая её часть не покрыта тестами, а косвенные изменения уже не раз значительно нарушали ключевые механики.

Есть доступный вспомогательный класс для тестов `AtmosTest`, который может помочь вам написать тесты для вашей функции.

### Улучшения производительности должны подтверждаться бенчмарком
Многократно было доказано (как моими собственными попытками улучшить производительность, так и чужими), что некоторые изменения производительности имеют мало эффекта или не имеют его вовсе.

Это досадно, так как большинство изменений производительности делали код более сложным и трудным для чтения — будь то через многопоточность, безветвевой код или векторизованный код.

Поэтому все улучшения производительности должны подтверждаться бенчмарком.
Вы обнаружите, что это фактически необходимо для осмысленной итерации по любой цели производительности, которую вы хотели бы достичь.
Это также сильно помогает будущим контрибьюторам опробовать свои собственные оптимизации производительности и уменьшает гипотетические рассуждения об изменениях контента, которые могут снизить производительность.

### Не скрывайте потенциальную численную нестабильность или шум
Когда пишете код для атмосферы, не игнорируйте потенциальную численную нестабильность, так как это может скрыть плохие крайние случаи во время тестирования или во время геймплея.
Например, если вы делите `HeatContainer` на \\( n \\) частей, убедитесь, что \\( n \\) — это `uint`, и используйте вспомогательные методы `ArgumentOutOfRangeException`, чтобы выбрасывать исключение, если \\( n = 0 \\):

```csharp
public static HeatContainer[] Divide(this HeatContainer c, uint num)
{
    ArgumentOutOfRangeException.ThrowIfZero(num);

    var fraction = 1f / num;
    [...]
```

Если ваш численный метод обладает естественной численной нестабильностью, которой не должно быть видно в геймплее (например, взорвавшаяся экспонента), обязательно либо ограничьте потенциальное значение известным диапазоном хороших значений, либо переключитесь на более стабильный метод — и при этом залогируйте ошибку, чтобы отслеживать это.

Неконтролируемая численная нестабильность приводит к более мучительной отладке, так как проблема распространяется вниз по стеку вызовов.
Это легко может привести к тому, что длительные этапы симуляции в атмосфере взорвутся.

Если вы делаете в коде допущение (например, пропускаете проверку на null, потому что знаете, что ваши данные не равны null), обязательно:
- Сделайте debug-assert (`DebugTools.Assert` или `DebugTools.AssertNotNull`) вашего условия.
- Продемонстрируйте, что любая логика, которую вы пропускаете, стоит того, чтобы её пропускать, с помощью бенчмарка.

### Крупные функции или состояния обработки должны быть как можно более настраиваемыми
При добавлении новой крупной функции убедитесь, что конкретное состояние обработки можно отключить через CVAR.

Значения `const`, которые не критичны для производительности или которые не должны часто меняться, можно превратить в CVAR.

Это позволяет форкам включать, отключать или иным образом настраивать определённые атмосферные этапы по своему усмотрению.
Форку не должно приходиться вырывать всю подсистему, если он хочет её отключить.

### Не прикрепляйте крупные функции к существующему состоянию обработки
При добавлении нового поведения для состояния обработки убедитесь, что вы не хардкодите фактически всё больше проверок и обработки логики.
Это делает логику негибкой, потому что если кто-то захочет добавить ещё одно поведение в функцию, ему, вероятно, придётся дописать ещё больше проверок к тем, что добавили вы.

Например, возьмём систему `Hotspot`, которая проверяет, разрешено ли тайлу начать газовый пожар на себе:

```csharp
if ((tile.Hotspot.Temperature < Atmospherics.FireMinimumTemperatureToExist) ||
    (tile.Hotspot.Volume <= 1f) ||
    tile.Air == null ||
    tile.Air.GetMoles(Gas.Oxygen) < 0.5f ||
    (tile.Air.GetMoles(Gas.Plasma) < 0.5f &&
    tile.Air.GetMoles(Gas.Tritium) < 0.5f))
{...}
```

Не добавляйте больше проверок в эту систему, чтобы сделать возможными пожары от реагентов, вот так:

```csharp
if ((tile.Hotspot.Temperature < Atmospherics.FireMinimumTemperatureToExist) ||
    (tile.Hotspot.Volume <= 1f) ||
    tile.Air == null ||
    tile.Air.GetMoles(Gas.Oxygen) < 0.5f ||
    (tile.Air.GetMoles(Gas.Plasma) < 0.5f &&
    tile.Air.GetMoles(Gas.Tritium) < 0.5f)) &&
    tile.SolutionFlammability == 0))
{...}
```

Вместо этого логику `Hotspot` следует переработать так, чтобы и газовые состояния, и состояния реагентов могли вносить вклад в общий показатель воспламеняемости, который повышает температуру тайла.
Это позволяет будущим контрибьюторам просто добавлять больше механик, влияющих на общую воспламеняемость тайла (например, ковёр или деревянная мебель, стоящая на тайле диона и т. д.).

Хардкодинг всё большего числа проверок в подсистему вместо создания собственной специализированной подсистемы или обобщения вкладов также означает, что будет труднее сделать вашу функцию настраиваемой/отключаемой.

### Логика атмосферы должна учитывать свой бюджет времени
Атмосфера распределяет свою обработку по нескольким тикам, чтобы смягчить удар, который она наносит по таймингу тика `EntitySystem`.
Из-за этого подсистемы должны учитывать, сколько времени прошло с начала тика, и при необходимости передавать обработку следующему тику обработки.

Обычно это делается с помощью секундомера симуляции в `AtmosphereSystem._simulationStopwatch`.
Состояния обработки проверяют этот секундомер каждые несколько секунд и уступают, если время обработки превысило бюджет на тик:
```csharp
private bool ProcessHotspots(
    Entity<GridAtmosphereComponent, GasTileOverlayComponent, MapGridComponent, TransformComponent> ent)
{
    var atmosphere = ent.Comp1;
    if(!atmosphere.ProcessingPaused)
        QueueRunTiles(atmosphere.CurrentRunTiles, atmosphere.HotspotTiles);

    var number = 0;
    while (atmosphere.CurrentRunTiles.TryDequeue(out var hotspot))
    {
        ProcessHotspot(ent, hotspot);

        if (number++ < LagCheckIterations)
            continue;

        number = 0;
        // Обработать остальное в следующий раз.
        if (_simulationStopwatch.Elapsed.TotalMilliseconds >= AtmosMaxProcessTime)
        {
            return false;
        }
    }

    return true;
}
```

Поэтому ваша подсистема не должна быть спроектирована так, чтобы ей приходилось выполнять весь свой этап симуляции за один раз; вместо этого она должна иметь возможность приостанавливать и возобновлять обработку на протяжении многих тиков.
Многие системы достигают этого, обрабатывая то, что нужно сделать, по единицам, и периодически проверяя секундомер, чтобы понять, вышло ли время.

Обратите внимание, что это усложняется для многопоточных и/или векторизованных этапов обработки — бенчмаркинг следует использовать, чтобы убедиться, что отдельные прогоны этапа обработки не превышают максимально допустимое время кардинально.

### По возможности переиспользуйте память - избегайте выделения в куче для симуляции
Когда пишете код для атмосферы, обращайте внимание на любые выделения памяти в куче, даже если это что-то вроде перечисления `foreach` или `List<T>`.

Выделения объектов создают ненужную нагрузку на сборщик мусора, особенно если указанные выделения объектов находятся в коде симуляции — коде, который выполняется каждый атмосферный тик.
Поэтому по возможности переиспользуйте память, например массивы.
Например, `AtmosphereSystem.Monstermos` хранит массивы для постановки тайлов в очередь и вычисления распространения давления:

```csharp
public sealed partial class AtmosphereSystem
{
    [Dependency] private readonly FirelockSystem _firelockSystem = default!;

    private readonly TileAtmosphereComparer _monstermosComparer = new();

    private readonly TileAtmosphere?[] _equalizeTiles = new TileAtmosphere[Atmospherics.MonstermosHardTileLimit];
    private readonly TileAtmosphere[] _equalizeGiverTiles = new TileAtmosphere[Atmospherics.MonstermosTileLimit];
    private readonly TileAtmosphere[] _equalizeTakerTiles = new TileAtmosphere[Atmospherics.MonstermosTileLimit];
    private readonly TileAtmosphere[] _equalizeQueue = new TileAtmosphere[Atmospherics.MonstermosTileLimit];
    private readonly TileAtmosphere[] _depressurizeTiles = new TileAtmosphere[Atmospherics.MonstermosHardTileLimit];
    private readonly TileAtmosphere[] _depressurizeSpaceTiles = new TileAtmosphere[Atmospherics.MonstermosHardTileLimit];
    private readonly TileAtmosphere[] _depressurizeProgressionOrder = new TileAtmosphere[Atmospherics.MonstermosHardTileLimit * 2];
    ... 
}
```

Обратите внимание, что начальные размеры массивов — все значения `const`, согласно ранее упомянутым конвенциям.

Поскольку вы обычно пишете для `Content.Server` и только для `Content.Server`, вы можете воспользоваться `stackalloc` и `ArrayPool`.
Обратите внимание, что при использовании `stackalloc` всегда следует быть очень осторожным, так как желаемый размер массива для ваших данных может переполнить стек.

В контекстах многопоточности (например, `IParallelRobustJob`) предпочтительнее использовать `ArrayPool`, чтобы быстро брать массивы напрокат.
Обязательно всегда возвращайте их в случае исключения.
